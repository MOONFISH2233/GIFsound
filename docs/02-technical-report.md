# 技术可行性与实测报告

> 所有数字来自本仓库的自动化脚本，可复现。原始数据在 `results/*.json`。
> 测试环境：Windows 11 / Node 24 / Playwright 1.62 / **HeadlessChrome 151.0.7922.34**。
> **单浏览器、无头模式、合成素材**——这些限制在 §7 明确列出，不要外推。

---

## 1. 做了什么

一个完整可运行的端到端原型：

```
assets/demo.gif            40 帧，帧延迟不均匀（60~140ms），底部有机器可读的帧号条码
assets/demo.wav            4.0 秒，44.1kHz 单声道 16bit，在帧 0/10/20/30 起点放 1kHz 提示音
assets/demo-audio.gif      把上面两个合成一个 .gif（383 KB）
```

工具链：

| 模块 | 作用 |
|---|---|
| `src/protocol.js` | FRAMEAUD 扩展块的构建 / 解析 / 结构校验 / 锚点反演 |
| `src/gif-parse.js` | GIF89a 结构解析、扩展块提取、trailer 前插入 |
| `src/gif-lzw.js` | LZW 解码（自研，无依赖） |
| `src/gif-encode.js` | GIF 编码 + LZW 编码（用于生成可控测试素材） |
| `src/node/make-assets.js` | 生成素材并注入 |
| `web/player.js` | 浏览器侧同步解码器（自绘渲染 + Web Audio） |
| `tools/measure-*.js` | 以合成器输出为真值的自动化测量 |

自检：`node test/run.js` —— **32 项全部通过**（LZW 编解码往返、结构解析、像素还原、协议校验、篡改检测）。

## 2. 协议设计

### 2.1 字节布局

```
0x21 0xFF 0x0B
"FRAMEAUD"     (8 字节 Application Identifier)
"0.1"          (3 字节 Authentication Code)
[0x01][JSON]   子块类型 1 = MANIFEST（可跨多个子块，按序拼接）
[0x02][bytes]  子块类型 2 = AUDIO（音频容器字节，可跨多个子块）
0x00
```

每个子块首字节是 chunk type，长度字节含该字节，故净载荷 ≤254 字节。

### 2.2 manifest

```json
{
  "v": 1,
  "frameCount": 40,
  "timescale": 1000,
  "cycleTicks": 4000,
  "frames": [80, 100, 120, ...],
  "anchors": [ { "frame": 0, "time": 0 }, { "frame": 1, "time": 80 }, ... ],
  "audio": { "codec": "pcm_s16le", "container": "wav",
             "sampleRate": 44100, "channels": 1, "bitsPerSample": 16,
             "byteLength": 352844 },
  "policy": { "onLoop": "restart", "onDetach": "silent" }
}
```

**核心是 `anchors`**：它把「第几帧」和「音频时间轴上的第几毫秒」显式绑定，是文件内的一等数据结构。

### 2.3 校验与降级

`verifyManifest()` 检查：协议版本、`frames.length == frameCount`、`cycleTicks == sum(frames)`、锚点严格单调、`audio.byteLength` 与实际字节数一致。任何一项不成立 → 解码器判定协议失效 → 静音降级。

这让「帧被裁剪/重编码后映射失效」是**可检测**的，而不是静默错位。

### 2.4 体积开销

| 项 | 字节 |
|---|---|
| 原始 GIF | 26,049 |
| 注入后 | 383,071 |
| 其中音频（WAV） | 352,844 |
| 扩展块结构开销 | ≈ 4,178（1.1%，来自子块长度字节与 manifest） |

WAV 是原型阶段的省事选择。若换 Opus（24 kbps），4 秒音频约 12 KB，整包可压到 ~38 KB。

## 3. 关键技术发现（实测，非推测）

### 3.1 `<img>` 对未知扩展完全透明

注入 345 KB 音频扩展后：

- `__img` 加载成功，`naturalWidth × naturalHeight` = 240×180，`complete = true`
- 播放正常（两次截图哈希不同，证明在动画）
- ffmpeg 交叉验证：40 帧、时长 4.000s、无解码错误

**这是本方案兼容性主张的直接证据。**

### 3.2 浏览器没有暴露「当前显示第几帧」的 API ★

这是整个项目最重要的一条发现。

对同一个动画 GIF：
- `ctx.drawImage(img, 0, 0)` 连续取 5 次，间隔 250ms → 读到的**全是第 0 帧**
- `createImageBitmap(img)` 连续 5 次 → **也全是第 0 帧**
- 但同一时刻对 `<img>` 元素截图，两次哈希不同 → **屏幕上的确在动**

结论：**画面在动，但 JS 拿到的永远是首帧。**

推论：任何「让音频去追原生 GIF 播放器」的方案，其同步时钟的相位在 JS 侧**根本不可观测**。这不是精度问题，是信息不可得问题。

这条也直接否定了原任务说明书里「利用 GCE 的 delay 值结合 rAF 时间戳估算当前帧号」的可行性——你可以估算，但永远无法校正，因为你拿不到真值。

### 3.3 原生播放器在空闲时其实很准

| 指标 | 值 |
|---|---|
| 实测周期 | 3999.95 ms（标称 4000） |
| 周期标准差 | 0.25 ms |
| 观测周期数 | 3 |

所以「延迟累积模型会漂移」这个说法在**空闲前台、单浏览器**下**不成立**。必须如实报告。

那 B1 的问题在哪？在**锚点**。

### 3.4 B1 的真实误差来自「相位未知」，不是「速率漂移」

以 `img.onload` 作为时钟锚点（这是页面真正能拿到的唯一东西），60fps 采样 950 个点：

| 指标 | 值 |
|---|---|
| 帧级错配率 | **10.0%** |
| 平均绝对误差 | 10.94 ms |
| P95 绝对误差 | **110 ms** |
| 最大绝对误差 | **140 ms** |

对照组：若给 B1 **oracle 相位**（遍历整个周期取最优锚点，现实中拿不到），误差恒为 **0**。

**两者之差就是「相位不可观测」的代价。** 140 ms 远超音画同步的感知阈值（约 45 ms），而且——关键——**出错时你无从知道**，因为没有真值可对照。

### 3.5 自绘方案：误差是系统性的、可测量的、可补偿的

以同一套合成器截图真值测量自绘播放器（840 个点，60fps）：

| 指标 | 无补偿 | 补偿 27ms |
|---|---|---|
| 帧切换滞后 平均 | **26.02 ms** | **4.43 ms** |
| 帧切换滞后 P95 | 31.94 ms | 27.04 ms |
| 帧切换滞后 最大 | 32.82 ms | 27.56 ms |
| 显示帧 vs 音频时间轴 错配率 | 17.0% | 13.0% |

26 ms 的来源很明确：帧在第 T 个 rAF 回调里被绘制，但用户要到 T+合成器延迟 才看到，而音频是按时间轴准点听到的。**画面天然落后音频约一个刷新周期。**

把取帧位置前移 27 ms 后，平均滞后降到 4.43 ms。这就是一条自然的从属权利要求：**根据呈现延迟预测，提前取帧**。

> 注意：错配率仍有 13%，因为采样间隔本身就是 16.7 ms，帧边界附近存在不可避免的判定模糊。**不要用「错配率」跨方案比较**——两个方案的误差分布形状不同（B1 是重尾，P 是有界但系统性）。可比的是绝对时间误差。

### 3.6 热切入是精确的（这是自绘架构真正的优势）

场景：页面加载后 GIF 无声自播 1.3 秒，用户此时点击解锁音频。

实测：

| 字段 | 值 |
|---|---|
| 解锁后音频偏移 | **1601.2 ms** |
| 当前帧窗口 | [1600, 1680) ms |
| 是否落在窗口内 | **是** |
| 调度误差 | 5.1 ms（即我们主动留的调度提前量） |

因为播放器自己知道时间轴位置，切入点是**算出来的**，不是估出来的。

而在 B1 架构下，这一步只能靠猜——参考 §3.4，猜测误差 P95 为 110 ms。

**结合浏览器的自动播放策略（必须用户手势才能起播），「音频与 GIF 同时开始」在现实中根本不成立。所有真实场景都是热切入。** 这是本方案最扎实的立足点。

### 3.7 一个被证伪的假设：切后台/隐藏并不会失步

原计划想证明「切后台后原生播放器掉队、音频继续跑」。实测**不支持**：

- 用 `display:none` 隐藏图片 2018 ms 再恢复
- 恢复瞬间的实际落后量：**7.52 ms**
- 隐藏前误差 4.65 ms，恢复后 5.12 ms

即 Chromium（无头）**没有**因为元素不可见而暂停动画。

> 这是负面结果。**不要再在论文或专利里写「切后台必然失步」**，除非补做有头模式 + 真实标签页切换的实验并拿到数据。目前没有该数据。

## 4. 修复的缺陷（开发记录）

| 缺陷 | 表现 | 根因 | 修法 |
|---|---|---|---|
| LZW 编码器 off-by-one | 自产 GIF 在 ffmpeg 里 40 帧全部 `LZW decode failed` | 解码器的字典恒比编码器落后一个条目（首个码不建表），码宽增长判据应为 `next > 2^codeSize` 而非 `===` | 改判据，加 2/4/8 bit × 随机/结构化数据的往返测试 |
| 时间轴跳变 | 帧号与墙钟差约 700 ms | 把 `getOutputTimestamp()` 当主时钟；在无音频输出设备的环境里，它返回的 `(contextTime, performanceTime)` 与 performance 时基有数百毫秒偏差 | 主时钟固定用 `performance.now()`，音频作为从属通过 `getOutputTimestamp()` 映射调度；每周期重新锚定，误差不跨周期累积 |
| demo 页状态不更新 | `<img>` 已加载但显示「等待加载」 | 模块脚本执行晚于 `load` 事件 | 先检查 `img.complete` 再决定是否挂监听 |

## 6. 对原方案的修正

原任务说明书的三层设计需要修正两层：

| 原设计 | 修正 |
|---|---|
| 第一层：时序绑定音频扩展块 | **保留**。这是唯一未被现有技术覆盖的点 |
| 第二层：监听原生 GIF 渲染时序，估算当前帧号 | **放弃**。§3.2 证明真值不可得；应改为**自绘渲染器**，由播放器拥有时钟 |
| 第三层：用户交互后从当前帧热切入 | **保留并升级为核心论点**。这是自绘架构唯一能做、而追原生播放器做不到的事 |

## 7. 局限（必须写进论文的限制章节）

1. **单浏览器**：只有 Chromium 151 无头。Firefox / WebKit 未测（安装包未就绪）。
2. **无头模式**：真实有头浏览器、真实音频设备的行为可能不同，尤其 `getOutputTimestamp()`。
3. **合成素材**：条码帧不是自然内容；真实 GIF 的帧内容复杂度、调色板规模不同。
4. **无感知实验**：没有做主观音画同步评分，45 ms 阈值引自文献而非本次实测。
5. **无跨浏览器 / 跨设备**：移动端、Safari 的 Web Audio 行为差异未覆盖。
6. **B1 的对比条件是偏向它的**：测试页只有一个 `<img>`，`img.onload` 几乎就是动画起点。真实页面（字体、布局、冷缓存、多个图片）里锚点会更差——但**本次没有测**，不能量化。
7. **扰动的负面结果**：隐藏元素未导致失步；真实标签页切换未测。
8. **扩展被剥离**：未跑 gifsicle / ImageMagick / ezgif 的实际链路测试（本机无 gifsicle）。
