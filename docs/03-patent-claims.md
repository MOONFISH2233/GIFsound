# 权利要求素材草案

> **这不是可提交的权利要求书。** 只是给专利代理师的技术素材。
> 每一条都标注了它被哪些现有技术覆盖——**标注为「已覆盖」的特征不能作为区别技术特征**。
>
> 综合评估：**本方向的授权前景不乐观**。若预算有限，建议先做一次正式检索再决定是否申请。

---

## 0. 一句话说明问题在哪

把方案拆成三个特征：

- **A** = 在 GIF Application Extension 内写音频块
- **B** = 音频块在文件内显式关联帧时序
- **C** = 浏览器侧 JS 解码器按该关联调度播放

| 组合 | 是否已被公开 | 被谁 |
|---|---|---|
| A | 是 | Habr 2012（`RIFFWAVE`）、audiogif 2019（`AUDIOGIF`）、SoundGIF 2026（`SNDGIF01`） |
| A + B | 是 | **gifed 2023 草案**（`GENNYBLE`/`AUD`，ACE/ADT，百分之一秒时基） |
| A + C | 是 | Habr 2012（jsgif 播放器）、SoundGIF 2026（单时钟 + 250ms 校正） |
| A + B + C | **未检索到单篇** | — |

审查员完全可以用「A+B」和「A+C」两份文献组合，主张 A+B+C 显而易见。
**因此独立权利要求不能只写 A+B+C，必须再叠加具体的、有技术效果支撑的区别特征。**

## 1. 候选区别特征（按可辩护性排序）

### 特征 D：呈现延迟补偿 —— 最有说服力

> 根据显示管线的呈现延迟 L，在时间点 T 选择「时间轴上 T+L 时刻对应的帧」进行绘制，
> 使该帧实际呈现的时刻与音频在 T+L 时刻的播放位置对齐。

**为什么它可能站得住**：
- 现有文献的播放器（audiogif、SoundGIF、gifed 草案）都是「按当前时刻取帧」，没有任何一篇补偿呈现延迟
- 有**实测支撑**：不补偿时平均滞后 26.02 ms，补偿 27 ms 后降到 4.43 ms（见技术报告 §3.5）
- 解决的是真实技术问题：合成器延迟导致画面系统性落后于音频

**风险**：游戏引擎、视频播放器中「按呈现延迟预测取帧」是成熟做法，审查员可能援引相邻领域文献。

### 特征 E：热切入的精确音频定位 —— 有说服力

> 在动画已开始播放的情况下，响应首次用户交互并解锁音频时，
> 由**播放端自身维护的时间轴位置**计算音频切入偏移，使音频从该偏移开始播放，
> 从而使切入后的音频位置与当前显示帧严格对应。

**为什么它可能站得住**：
- 浏览器自动播放策略决定了「音频与动画同时开始」在真实场景中不可能，**必然**是热切入
- 现有方案（audiogif、SoundGIF）的切入依赖「当前帧」或「当前时间」的估计
- 有**实测支撑**：切入偏移 1601.2 ms 精确落在当前帧窗口 [1600, 1680) 内

**风险**：若以「媒体恢复播放时按位置续播」为上位概念，属通用技术。

### 特征 F：映射失效的可检测降级

> 播放端解析 manifest 后，交叉校验帧数、周期总长、音频字节长度三项；
> 任一不符即判定帧-音频映射已失效，并转入静音播放模式。

**为什么它可能站得住**：
- 现有文献都假设映射永远有效，没有处理 GIF 被重编码导致帧数变化的情形
- 解决真实问题：GIF 优化工具会删帧/合并帧，使帧索引错位

**风险**：属于常规的数据完整性校验，创造性弱。

### 特征 G：单周期重锚定的音频调度

> 每个动画周期单独调度一次音频源，起点按周期边界计算，使误差不跨周期累积。

**风险**：SoundGIF 2026 已实现「每个 GIF 周期重启音频」，**已覆盖**。

## 2. 独立权利要求素材（方法）

> 已按最大限度的区别特征组合撰写，范围很窄。这是为了最大化授权概率而牺牲范围的写法。

**权利要求 1（方法）**

一种为动画 GIF 提供同步音频的方法，其特征在于，包括：

在 GIF 文件的 Application Extension 中写入多个音频块，每个音频块关联所述 GIF 动画中至少一个帧的时序信息；

播放端以二进制方式读取所述 GIF 文件，解析所述音频块及其时序信息，并由播放端自身维护一条播放时间轴；

播放端通过自身渲染管线逐帧绘制所述 GIF 动画，并在**时间点 T 选择所述时间轴上 T+L 时刻所对应的帧**进行绘制，其中 L 为所述渲染管线的呈现延迟估计值，使该帧实际呈现的时刻与音频在 T+L 时刻的位置对齐；

其中，当所述 GIF 动画在音频解锁之前已经开始播放时，播放端根据所述播放时间轴的当前位置计算音频切入偏移，并从该偏移处开始播放音频。

> **区别技术特征**：呈现延迟补偿（L）+ 热切入按已知时间轴定位。
> 与 gifed 2023 的差异：gifed 只定义文件结构，不涉及浏览器侧同步；
> 与 SoundGIF 2026 的差异：SoundGIF 用音频时钟反馈校正，不做呈现延迟预测，也无文件内帧映射。

## 4. 建议的权项布局

若仍要申请，建议：

1. **不要**写「一种有声 GIF 格式」——纯数据格式在中国有客体风险（《专利法》第 25 条）
2. 以**方法**为主，绑定「解决 GIF 无法携带音频导致额外请求与音画不同步」的具体技术问题
3. 装置权项写成「一种播放装置，包括解析模块、渲染模块、调度模块」
4. 存储介质权项同步布局
5. **把特征 D 和 E 全部塞进独立权利要求**——范围窄但活得下来，比范围宽被驳回好

## 5. 建议的前置动作

1. 调取 **CN105261054A 的审查档案**，看驳回理由是否涉及客体或创造性——这是同方向的强预警
2. 正式检索 **gifed 2023 草案**的完整内容（本环境被网络策略拦截，未核验原文）
3. 评估 **CN110505511B**（已授权，帧索引→音频偏移）与 **CN108616768B**（腾讯，有效至 2038）的 FTO 风险
4. 考虑改变策略：不做「格式 + 播放器」的组合专利，改做**更窄的装置专利**（例如只针对热切入同步的播放装置）

## 6. 诚实的结论

按现有技术分布，本方案更接近**工程改进**而非**可授权的发明**。
如果目标是「有一份专利」，需要接受范围极窄、且仍可能被驳回；
如果目标是「有学术产出」，建议转向论文路线（见 `04-paper-plan.md`），
把「原生 GIF 帧时序不可观测」这个测量结果作为核心贡献——**这一点目前确实没有人系统测量过**。
