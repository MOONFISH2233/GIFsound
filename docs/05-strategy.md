## 一、论文：能发，但必须换定位

### 能站住的贡献

**「动画图像的当前帧对 JavaScript 不可观测」是一个可验证的事实**，而且此前没有人系统测量过。

已完成的实验（Chromium）：

| 格式 | 屏幕上在动 | drawImage 能读到的不同帧数 | createImageBitmap |
|---|---|---|---|
| GIF | 是 | **1** | **1** |
| APNG | 是 | **1** | **1** |
| 动画 WebP | 是 | **1** | **1** |

**这不是 GIF 的缺陷，是「动画图像」这一类载体的共性。** 这个结论比原方案大得多。

再加一个决定性的对照——同一个页面里：

| 媒体 | 能读到播放位置 | 不同取值数 |
|---|---|---|
| `<video>` | `currentTime` | 6 / 6 |
| CSS 动画 | `getAnimations()[0].currentTime` | 6 / 6 |
| 动画图像 `<img>` | **无** | **0** |

**「不可观测」是浏览器在动画图像上的设计选择，不是渲染管线做不到。**
这句话把论文从「我们遇到一个坑」抬到「我们指出了一个 API 设计空白」。

配套的量化结果：

- 原生播放器本身很准（周期 3999.95ms vs 标称 4000，标准差 0.25ms）
- 但用页面唯一可得的锚点（`img.onload`）推算，帧级错配率 10%、P95 误差 110ms
- 给 oracle 相位则误差为 0 —— **差距完全来自相位不可观测**

### 不能写的

- ❌「首次给 GIF 加音频」（Habr 2012 就有）
- ❌「首次在 Application Extension 里放音频」（audiogif 2019）
- ❌「首次做帧锚定映射」（gifed 2023 草案）
- ❌「切后台会失步」（实测不掉队，7.52ms）

### 定位

**测量研究**，不是系统发明。标题方向：

> *You Cannot See Frame N: Measuring the Limits of Audio-Visual Synchronization in Legacy Animated Images*

### 投稿前必须补的

| 优先级 | 实验 | 工作量 |
|---|---|---|
| P0 | 跨浏览器（Firefox / WebKit） | 脚本已支持，装完浏览器即跑 |
| P0 | 有头模式 + 真实音频设备 | 半天 |
| P1 | 真实素材（换掉条码帧） | 1 天 |
| P1 | 感知阈值实验（20 人 ABX） | 1 周 |
| P2 | 优化工具链路（gifsicle / ImageMagick） | 1 天 |

**结论：一篇 workshop / 会议短文是可行的，3–4 周工作量。上 CCF-B 以上的期刊，贡献体量不够。**

## 二、专利：不建议作为主目标

| 特征 | 被谁覆盖 |
|---|---|
| 扩展块内写音频 | Habr 2012、audiogif 2019、SoundGIF 2026 |
| 音频块关联帧时序 | **gifed 2023 草案** |
| 浏览器 JS 单时钟播放 | Habr 2012、SoundGIF 2026 |
| 每周期重启音频 | SoundGIF 2026 |
| CRC 校验 | SoundGIF 2026 |

剩下只有三个很窄的工程细节：

1. 呈现延迟预测与提前取帧
2. 热切入按已知时间轴精确定位
3. manifest 交叉校验与可检测降级

这三条**单独都不足以支撑一个有力的独立权利要求**。「按呈现延迟提前取帧」在游戏引擎里是成熟做法，审查员很容易援引。

**如果一定要申请**：写窄（把 1+2 全塞进独权）、以方法+装置+存储介质三套布局、预算控制在可承受范围，并做好被驳回的心理准备。先花几千块做一次正式检索再决定。

## 三、往哪发散：四个方向，按推荐度排序

### ⭐ 方向 A：跨格式动画图像的播放可观测性（**已在做，强烈推荐**）

**问题**：浏览器对 GIF / APNG / WebP / AVIF 动画的当前帧都不暴露给 JS。这意味着：

- 任何需要与动画帧同步的应用（音画同步、逐帧标注、可访问性字幕、自动化测试）都做不到
- 现有的 Web API 没有任何替代方案

**可做的**：
- 补齐 Firefox / WebKit 数据 → 得到「所有主流引擎都不暴露」的强结论
- 补齐 AVIF 动图
- 测量 CSS 动画、`<video>` 作为对照（它们**能**观测），说明这是设计选择而非技术限制

**产出**：一篇扎实的测量论文。**新颖性最高、成本最低。**

### ⭐ 方向 B：浏览器合成器呈现延迟的测量与补偿

**问题**：JS 在 `requestAnimationFrame` 里画的帧，要过多久才真正显示？实测约 26ms（Chromium 无头）。
这对任何「canvas 动画 + 音频」的应用都是系统性偏移。

**可做的**：
- 跨浏览器 × 跨刷新率（60/120/144Hz）测量
- 提出自适应补偿方法（现在是硬编码 27ms）
- 与输入延迟研究对照（那一块研究很成熟，输出侧相对少）

**产出**：论文的第二章，也可以单独成文。**工程价值高，可复用。**

### 方向 C：动画图像的帧时序指纹

**想法**：GIF 的帧延迟模式（60/80/100/140ms 的组合）在重编码后**往往被保留或只被量化**，而像素会被彻底改变。
所以「帧时序序列」可能是一种比像素水印更抗转码的指纹/水印载体。

**可做的**：
- 测量常见链路（gifsicle、ImageMagick、平台转码）后延迟序列的幸存率
- 设计满足感知约束的编码方式

**风险**：已有 CN107103630B 把 GCE 属性做区间映射编码；需要先做正式检索。
**与主线相关性高，但属于安全/取证领域，要换一套评价指标。**

### 方向 D：面向可访问性的动画图像描述

给无声 GIF 生成字幕/文字描述并在正确的时间点呈现 —— 同样受「帧不可观测」制约。
属于 HCI/无障碍，需要用户研究。

**推荐顺序：A → B → C。** D 与当前技术积累关系最远。

## 四、如果只能做一件事

**做 A。**

理由：
1. 实验已经跑通，成本最低
2. 结论最硬（可验证的事实，不依赖方案优劣）
3. 跨格式 + 跨浏览器，覆盖面广
4. 是 B 和 C 的共同基础

## 五、如果目标是「必须有专利」

建议**放弃这个题目**，换一个能独立成立的发明点。
在「帧不可观测」这个约束下，能独立成立的专利方向更像是：

- 一种**播放装置**：在无法观测原生播放状态时，通过自建渲染管线 + 单一时间轴实现精确同步（即本原型，写窄）
- 一种**同步就绪检测**方法：在素材加载完成但尚未开始呈现的窗口内完成音频预调度

两者都需要专业检索确认，且都属「工程改进」层级的创造性。
